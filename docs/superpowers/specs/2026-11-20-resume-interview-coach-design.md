# 이력서 기반 AI 면접 코치 MVP 설계안

- 작성일: 2026-11-20 (Asia/Seoul)
- 상태: **사용자 승인 완료 — 2026-11-20**
- 목표: 활성 Goal의 전체 범위를 구현한다. 설계 승인이나 모의 테스트 성공만으로 Goal을 완료하지 않는다.

## 1. 목적과 합의된 원칙

이력서에 적힌 구체적인 경험을 출발점으로 질문하고, 사용자가 자신의 선택과 경험을 설명하도록 돕는 백엔드 면접 코치다. 이력서는 정답지가 아니다.

사용자와 대화 및 Goal에서 확정한 요구사항:

- 이력서 텍스트를 입력하고 저장한다.
- 이력서의 구체적인 내용을 근거로 기본 질문 **정확히 5개**를 생성한다.
- 답변의 기술적 정확성, 근거, 설명력을 평가한다.
- 정보가 부족하면 꼬리 질문을 최대 1회 생성한다.
- 질문, 답변, 평가를 저장하고 다시 조회한다.
- Claude 대신 무료로 사용할 수 있는 외부 AI API **1개**를 연동한다.
- 모범답안과 다른 이유로 감점하지 않는다. 익숙한 기술을 선택한 것도 맥락에 따라 유효한 근거다.
- 근거 부족과 명백한 오류를 구분한다. 확인할 수 없는 사실은 판단을 유보한다.
- 설명이 부족하면 부족하다고, 명백한 오류는 잘못이라고 말한다. 모든 답변을 합리화하지 않는다.
- 실제 경험이나 성능 수치의 진위를 검증했다고 주장하지 않는다.
- 다른 사용자의 이력서, 세션, 질문, 답변, 평가에는 접근할 수 없어야 한다.
- AI 호출 실패를 정상 평가로 저장하지 않는다.
- 주요 흐름과 실패 처리 테스트가 통과해야 한다.

제외: PDF, 음성, 프런트엔드, 배포, 벡터 DB/RAG, 여러 API 동시 지원, 유료 API 자동 전환.

## 2. 현재 코드에서 확인한 사실

- Java 17을 대상으로 하는 Spring Boot 4.1.0 / JPA / MySQL 백엔드다. 현재 실행 환경의 Java는 21이다.
- JWT와 BCrypt 인증이 구현되어 있다.
- SessionService는 categoryId로 세션을 만들고 해당 카테고리의 모든 고정 질문을 반환한다.
- Question에는 카테고리와 본문만 있고 세션과의 연결은 없다.
- AnswerService는 세션 소유권을 검사하지만 질문이 해당 세션의 것인지는 검사하지 않는다.
- ClaudeService는 문자열 형식 응답을 파싱하며 점수가 누락되거나 파싱에 실패하면 기본값 5가 저장될 수 있다.
- 외부 AI 호출이 답변 저장 트랜잭션 내부에 있다.
- 세션 목록과 완료 API는 있지만 질문·답변·평가를 포함하는 세션 상세 API는 없다.
- StatsService는 모든 질문에 카테고리가 있다고 가정한다.
- 테스트는 contextLoads 하나뿐이다. `./mvnw -o -Dspring.profiles.active=test test`로 기준선을 확인했고, 테스트 1개가 실패/오류 없이 통과했다. 이는 컨텍스트 로딩 증거이며 기존 API의 기능 검증이나 신규 요구사항의 완료 증거가 아니다.
- 설계 시작 시 git 작업 트리는 깨끗했다. 실제 키나 개인 이력서는 열람하지 않았다.

## 3. 접근 방식과 제안 선택

### 면접 진행 방식

1. **답변별 즉시 평가 + 필요한 경우 1회 확인 질문 (추천안)**
   - 기본 질문 5개를 먼저 저장한다. 각 답변 직후 평가와 선택적인 꼬리 질문을 반환한다.
   - 정보가 부족할 때 사용자에게 바로 확인할 수 있다. HTTP 요청당 기다리는 시간은 생긴다.
2. 모든 답변을 모아 마지막에 일괄 평가
   - 중간에 평가가 흐름을 끊지 않지만, 답변에 따른 추가 확인이 늦고 상태 관리가 더 복잡하다.

설계자 제안은 1번이며, 사용자가 2026-11-20에 "설계대로 구현해줘"라고 답하여 확정했다.

### API 제공자

- **Groq 무료 플랜**을 제안한다. 구체적인 모델은 연동 시 무료 계정에서 사용 가능하며 구조화 출력을 지원하는지 확인 후 하나로 고정한다.
- Gemini 무료 API도 후보지만 무료 입력 데이터 사용 조건 때문에 실제 이력서 서비스의 기본안으로 선택하지 않았다.
- 무료 한도나 한국어 평가 품질은 보장하지 않는다. 가상 데이터로 실제 응답을 검증한다.
- 사용자가 설계를 승인하여 Groq 연동으로 확정했다.

## 4. 승인받을 설계자 제안

아래는 설계자가 제안했으며 사용자 설계 승인으로 확정된 세부 결정이다.

- 꼬리 질문은 **기본 질문 하나당 최대 1개**다. 꼬리 질문의 꼬리 질문은 만들지 않는다. 총 질문은 5~10개다.
- 신규 평가에서는 단일 숫자 점수 대신 항목별 판정과 구체적인 피드백을 제공한다. 기존 답변 점수는 보존한다.
- 새 세션은 이력서 기반으로만 생성한다. 기존 고정 문제와 과거 세션은 삭제하지 않으며 과거 기록 조회를 보존한다. 구형 categoryId만으로 새 세션을 만드는 요청은 입력 오류로 안내한다.
- 이력서는 수정하지 않는 스냅샷으로 저장한다. 새 버전은 새 이력서를 등록한다. 이번 MVP에 편집·삭제 API는 추가하지 않는다.
- 기본 질문 5개를 미리 제시한다. 엄격한 순서 강제는 하지 않으며, 질문당 원답과 선택적 꼬리 답변을 각각 한 번만 받는다.
- 완료 처리는 사용자의 명시적 요청으로 수행한다. 미답변이 있어도 종료할 수 있고, 종료 후 새 답변은 받지 않는다. 미답변/추가 확인 미완료는 조회에 그대로 표시한다.

## 5. 사용자 흐름과 API 계약

```text
이력서 텍스트 등록
→ 저장된 내 이력서로 면접 시작
→ 이력서 근거를 가진 기본 질문 5개 저장·반환
→ 질문에 답변 제출
→ 오류·근거·설명력 피드백 저장·반환
  ├─ 설명 충분: 추가 질문 없음
  └─ 정보 부족: 저장된 꼬리 질문 1개 반환
       → 꼬리 답변 제출
       → 원답과 꼬리 답변을 함께 평가, 추가 질문 없음
→ 세션 상세에서 전체 기록 조회
→ 필요할 때 세션 완료
```

| API | 계약 |
| --- | --- |
| POST /api/resumes | text를 검증하고 소유자와 함께 저장. id, text, createdAt 반환 |
| GET /api/resumes | 내 이력서 목록(본문 제외한 요약 메타데이터) |
| GET /api/resumes/{id} | 내 이력서 원문과 메타데이터 |
| POST /api/sessions | resumeId 필수. 내 이력서인지 확인 후 질문 5개 생성, 원자적으로 저장 |
| GET /api/sessions | 내 세션 목록. 이력서 기반/기존 세션을 구분 |
| GET /api/sessions/{id} | 내 세션, 사용한 이력서 스냅샷, 순서가 있는 질문과 원답·평가·꼬리 질문·꼬리 답변 |
| POST /api/answers | sessionId, questionId, userAnswer. 소유권·질문 소속·종료·중복을 검증 |
| PATCH /api/sessions/{id}/done | 내 진행 중 세션 완료. 반복 완료는 기존 정책대로 거부 |
| GET /api/stats | 기존 점수 통계를 유지. 점수가 없는 신규 항목은 평균에 포함하지 않음 |

모든 위 API는 인증이 필요하다. 다른 사용자 소유 자원은 존재 여부를 드러내지 않는 404로 처리한다. 필수값 누락·공백·과도한 길이는 400, 중복 답변은 409다. 구체적인 길이 상한은 구현자가 정하되 문서와 테스트에 반영한다.

## 6. 데이터 모델 및 과거 기록

기존 엔티티를 필요한 만큼 확장하고, 새로운 저장 구조는 Resume만 추가하는 것을 기본안으로 한다.

- **Resume**: id, user, text, createdAt. 원문은 불변이며 생성 질문의 근거 검증에 사용한다.
- **Session**: 기존 user/status/createdAt 유지, resume 연결 추가. 구형 세션은 resume가 없다. 신규 이력서 세션은 category가 없어도 된다.
- **Question**: 기존 content/category 유지, session, 순서, 이력서 근거 인용문, 질문 의도, 평가할 요소, 선택적 parentQuestion 추가. 구형 고정 질문은 session이 없고 신규 생성 질문은 session이 필수다. 꼬리 질문은 같은 세션의 기본 질문만 부모로 가질 수 있다.
- **Answer**: 기존 userAnswer/feedback/score/createdAt 보존, 신규 항목별 평가 저장을 추가한다. 신규 score는 null로 두며 실패 시 기본 점수를 만들지 않는다.
- 기본 질문의 초기 평가는 보존한다. 꼬리 답변의 평가는 원답+꼬리 답변을 함께 본 결과이며 조회에서 이를 최신 종합 판단으로 명확히 구분한다. 원답 내용을 덮어쓰지 않는다.
- 신규 질문의 category가 없을 수 있으므로 DTO와 통계가 null을 안전하게 처리해야 한다. 기존 평균은 점수가 있는 과거 답변만 집계하며 신규 세션 수는 세션 통계에 반영한다. 응답/문서에 평균의 집계 대상을 명시한다.
- 기존 데이터의 카테고리·질문·세션·답변을 일괄 삭제하거나 새 모델로 추측 변환하지 않는다.
- 제약조건이나 컬럼 변경 전 기존 데이터와 MySQL 스키마를 확인한다. 실제 DB 접근 없이 운영 데이터 마이그레이션이 검증됐다고 주장하지 않는다. 기존 ddl-auto=update만으로 변경이 안전하다고 가정하지 않는다.
- 구현자가 컬럼 타입·인덱스·DB 제약·마이그레이션 스크립트의 최소 형태를 결정하되 데이터 보존과 아래 동시성 불변식을 충족해야 한다.

## 7. 질문 생성과 평가 계약

### 기본 질문 생성

AI에 저장된 이력서와 지침을 분리해 전달하고 다음 구조의 질문을 정확히 5개 요청한다.

- 본문
- 이력서의 실제 부분 문자열인 근거 인용문
- 질문 의도
- 평가할 요소 목록(모범답안이 아닌 관찰 기준)

서버는 개수, 필수값, 길이, 중복 질문, 인용문이 실제 원문에 존재하는지 검증한다. 이력서에 없는 기술이나 경험을 있었다고 전제하지 않도록 지침을 둔다. 의미상 근거의 적절성은 실제 샘플로 별도 검토하며 부분 문자열 일치만으로 품질이 입증됐다고 주장하지 않는다.

경험이 없는 한 줄, 무관한 문장 등으로는 질문 5개를 근거 있게 만들 수 없다. 생성 불가 결과를 정상 질문으로 바꾸거나 채우지 않고 422로 더 구체적인 이력서 입력을 안내한다. 모델이 출력 형식을 어긴 경우는 이력서 잘못이라고 단정하지 않고 AI 응답 오류로 처리한다.

### 답변 평가

AI에는 해당 이력서 근거, 질문·의도·평가 요소, 실제 답변을 보낸다. 꼬리 답변에서는 원질문/원답/초기 평가/꼬리 질문/꼬리 답변도 전달한다.

구조화 응답:

- technicalAccuracy: CORRECT / INCORRECT / NOT_ASSESSABLE
- reasoning: SUFFICIENT / INSUFFICIENT / INVALID
- clarity: CLEAR / UNCLEAR
- strengths: 구체적인 장점 목록(없으면 빈 목록 가능)
- improvements: 부족하거나 잘못된 부분과 개선 방향 목록
- uncertainties: 실제 사실 또는 현재 정보로 확인할 수 없는 부분 목록
- summary: 핵심 피드백
- followUpQuestion: 추가 정보가 필요할 때의 질문, 필요 없거나 이미 꼬리 답변 단계라면 null

판정 지침:

- 특정 기술을 선택하지 않았거나 비교표를 말하지 않았다는 이유만으로 부정 평가하지 않는다.
- "할 줄 아는 게 Redis뿐"은 자동 오답도 자동 정당화도 아니다. 요구사항 적합성을 설명했는지 확인한다.
- 선택 이유 미설명은 INSUFFICIENT, 기술적 오류나 논리적으로 무효한 근거는 INCORRECT/INVALID로 명확히 지적한다.
- 이미 확인된 오류는 꼬리 질문이 있더라도 평가에서 숨기지 않는다.
- 경험 진위·본인 기여의 사실 여부·측정 수치의 진위를 입증했다고 말하지 않는다.
- 입력에 없는 사실이나 선택 이유를 사용자 대신 만들어 주지 않는다. 하지 않은 검증을 했다고 답하도록 유도하지 않는다.
- 기술적 판단에 정보가 없으면 NOT_ASSESSABLE을 사용한다. 이것 자체가 AI 호출 실패는 아니다.
- 꼬리 질문은 설명 부족에 필요한 확인 질문이다. 충분한 답변에 불필요한 질문을 강제하지 않는다.
- 꼬리 답변 후에도 불충분하면 그 한계를 그대로 평가하고 종료한다.

각 필드의 타입·열거값·필수값·길이를 서버에서도 검증한다. 평가 기준과 프롬프트는 버전 상수로 관리하고 결과에 사용 모델/기준 버전을 남긴다. 형식 검증은 의미적 정확성 보장이 아니다.

## 8. AI 호출, 저장 경계와 동시성

- DB 읽기·권한 확인, 외부 HTTP 호출, 짧은 결과 저장 트랜잭션을 분리한다. 네트워크 대기 중 DB 트랜잭션/잠금을 유지하지 않는다.
- 질문 생성 성공 및 검증 후에만 세션+기본 질문 5개를 한 트랜잭션으로 저장한다. 실패하면 유효한 세션이나 일부 질문을 남기지 않는다.
- 평가 성공 및 검증 후에만 답변+평가+선택적 꼬리 질문을 한 트랜잭션으로 저장한다. AI 실패 시 답변을 성공 저장한 것처럼 응답하지 않는다. 클라이언트는 입력을 보존하고 다시 제출할 수 있다.
- 저장 직전에 소유권·진행 상태·질문 소속·중복을 다시 확인한다. 동시 완료 후 늦게 도착한 평가는 저장하지 않는다.
- 동시에 같은 질문에 답하더라도 저장되는 답변은 하나다. 같은 기본 질문의 꼬리 질문도 하나다. DB 제약 또는 짧은 저장 시 잠금으로 보장하고 동시성 테스트로 확인한다. 구현자가 가장 작은 올바른 방법을 선택한다.
- 기본 질문과 꼬리 질문 모두 해당 세션의 사용자만 접근한다. 임의의 기존 고정 질문 ID로 신규 세션에 답할 수 없다.
- 중복 HTTP 요청이 동시에 AI를 호출하는 비용까지 완전히 제거하는 작업 큐/잡 시스템은 MVP 밖이다. 중복 저장은 반드시 막는다.

실패 응답은 API 키/입력/제공자 원문을 포함하지 않는 안정적인 코드와 안내를 반환한다.

| 실패 | 처리 |
| --- | --- |
| 키 미설정/제공자 인증 실패 | 서비스 사용 불가 안내, 정상 결과 저장 없음 |
| 무료 한도/429 | 제한 안내, 자동 모델 전환·자동 재호출 없음 |
| 타임아웃 | 유한한 연결·응답 제한 후 실패 안내 |
| HTTP 오류/빈 응답/거부/출력 잘림 | AI 오류로 처리, 정상 결과 저장 없음 |
| JSON 파싱/필수값/범위/질문 수·근거 검증 실패 | AI 응답 오류, 정상 결과 저장 없음 |

타임아웃·외부 오류의 세부 HTTP 상태와 코드 명칭은 구현자가 결정하고 테스트/README에 명시한다. 검증 실패를 정상 피드백 또는 점수로 대체하지 않는다.

## 9. 무료 사용과 개인정보 경계

- Groq 공식 엔드포인트 하나와 선택한 모델 하나만 사용한다. Claude 호출과 설정은 신규 기능에서 제거한다. 다른 제공자로 fallback하지 않는다.
- 무료 플랜은 제공자 계정 상태다. 앱이 모델명만으로 무료 과금을 강제하거나 계정의 유료 업그레이드를 방지할 수는 없다.
- 실제 호출 전 사용자가 무료 플랜 및 해당 모델 무료 접근을 확인한다. 유료 계정으로 업그레이드하지 않으며, 키 제공은 로컬 비밀 설정을 사용한다. 채팅에 키를 붙여 넣도록 요구하지 않는다.
- 키가 없더라도 모의 HTTP 서버 기반 통합 테스트는 가능하다. **모의 성공을 실제 Groq 연동 검증으로 보고하지 않는다.** 최종 완료에는 무료 계정에서 가상 이력서로 생성과 평가 실제 호출이 성공한 증거가 필요하다.
- 이력서와 답변은 외부 제공자에게 전송된다. MVP 안내에 이를 명시하고 가상/비식별 테스트 데이터를 권장한다. 이름 삭제만으로 익명성이 보장된다고 주장하지 않는다.
- API 키, 이력서, 사용자 답변, 평가 원문을 일반 로그에 남기지 않는다. AI 오류 원문도 사용자나 일반 로그에 노출하지 않는다.
- 평가 지침과 사용자 입력을 분리하고 입력 내 "만점 처리" 등 명령을 따르지 않게 한다. 모델에게 외부 도구·DB·비밀 접근 권한은 주지 않는다. 프롬프트만으로 조작을 완전히 방지한다고 주장하지 않는다.

## 10. 완료 증거와 테스트 범위

| 요구사항 | 필요한 증거 |
| --- | --- |
| 이력서 입력·저장·조회 | 인증된 HTTP 테스트와 재조회 결과, 공백/길이 검증 |
| 근거 있는 질문 정확히 5개 | 정상 생성 테스트, 잘못된 개수/중복/허구 인용문 거부, 실제 응답의 의미적 검토 |
| 항목별 평가 원칙 | 프롬프트 계약 테스트와 실제 샘플 검토. 비정석이지만 타당한 답변/근거 부족/명백한 오류를 구분 |
| 꼬리 질문 최대 1회 | 원답→꼬리→재평가 통합 테스트, 두 번째 꼬리/중복/동시 요청 거부 |
| 기록 재조회 | 저장 후 별도 요청에서 원답·초기 평가·꼬리·종합 평가가 모두 보이는 HTTP 테스트 |
| 다른 사용자 접근 차단 | 두 사용자로 이력서/세션/질문/답변 읽기·쓰기 및 ID 혼합 공격 테스트 |
| 실패는 정상 결과 아님 | 401/429/5xx/타임아웃/거부/잘린 응답/잘못된 JSON 후 DB에 부분 결과가 없는지 확인 |
| 완료 후 불변성 | 종료 세션 답변 거부, 외부 호출 중 종료되는 경합 테스트 |
| 과거 기록 보존 | 기존 카테고리·고정 질문·답변 조회 및 신규 null category/score 통계 회귀 테스트 |
| 무료 API 실제 연동 | 사용자가 확인한 Groq 무료 계정으로 가상 이력서 생성·평가·필요 시 꼬리 평가 성공 |
| 전체 흐름 | 가입→로그인→이력서→세션→답변→조회→완료→재조회 자동화 테스트 |

가상 샘플은 최소 세 종류: (1) 익숙함/일정으로 선택했으나 요구사항 적합성을 설명하는 답변, (2) 이유가 모호하고 정보가 부족한 답변, (3) 명백한 기술적 일반화 오류가 있는 답변. 실제 모델 응답의 정확한 문구나 점수를 자동 테스트 정답으로 고정하지 않는다.

빌드/자동화 테스트, 실제 Groq 호출, MySQL 스키마 검증의 결과는 서로 구분하여 보고한다. 사용 키/서비스 접근이 없거나 설계 승인이 없으면 Goal을 완료하지 않는다.

## 11. 이후 절차

1. 설계 검토에서 누락된 결정만 보완한다.
2. 사용자에게 Groq, 질문별 1회 꼬리 질문, 숫자 없는 항목별 평가를 포함한 본 설계 승인을 요청한다.
3. 승인 후 구현 계획을 작성하고 테스트 주도로 최소 변경한다.
4. 실제 무료 계정 호출까지 검증하고 요구사항별 완료 감사를 수행한다.

설계 승인 대기 중 제품 코드를 수정하거나 API 키를 만들거나 실제 호출하지 않는다.

## 12. 설계 단계 검증 기록

- 2026-11-20: 별도 builder-check 에이전트가 문서와 현재 구조를 검토했고, 구현 계획 전에 답이 필요한 중요한 누락은 없다고 보고했다. 사용자 승인 자체를 대체하는 검토가 아니다.
