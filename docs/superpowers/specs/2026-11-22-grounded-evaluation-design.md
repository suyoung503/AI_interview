프롬프트만 보완하는 대신 평가 응답 구조도 변경하기로 선택했다.
가상 데이터로 기존 v4와 v5를 각 10회, 총 최대 20회 실제 Groq 호출하는 데 승인했다.
실제 플랜 유료 전환·자동 실패 재시도·다른 제공자 대체는 하지 않는다. 오류 시 실제 호출을 중단한다.
추가로 저장소 루트의 portfolio.md를 로컬 전용으로 작성한다. 로컬 info/exclude에 /portfolio.md를 등록했다.
이번 요청은 커밋까지이며 자동 push/main merge는 포함하지 않는다.

## 문제
v4 실제 웹 검증에서 캐시 처리 순서를 정확히 설명했다고 평가하면서 같은 설명을 개선점으로 다시 요구했다.
전체 판정은 정확함/근거 부족/명확함이었다. 세 축 전체가 긍정일 때만 배열을 지우는 기존 정책으로는
한 축만 부족한 경우 다른 축에 대한 불필요한 지적을 분리할 수 없다.

## 접근 방식과 선택
1. 프롬프트 자체 검토만 강화: 작지만 판단 근거와 결핍을 서버에서 구분할 수 없다.
2. **선택: 항목별 근거를 구조화하고 서버가 표시 정책을 적용.** 기존 평가 3축과 외부 평탄 필드는 유지하고
   근거 필드를 추가한다. 의미적 판단은 AI에 남기되 인용/형식/축별 허용 범위는 서버가 검사한다.
3. Redis 키워드/문장 유사도 필터·두 번째 AI 심사 호출: 다른 질문으로 일반화하기 어렵거나 비용·지연이 늘어 제외한다.

## v5 제공자 출력
기존 세 판정값 technicalAccuracy/reasoning/clarity를 유지한다.
제공자는 평탄한 strengths/improvements/summary를 따로 생성하지 않는다. 대신 assessments를 정확히 3개 출력한다.

```json
{
  "technicalAccuracy": "CORRECT",
  "reasoning": "INSUFFICIENT",
  "clarity": "CLEAR",
  "assessments": [
    {
      "axis": "TECHNICAL_ACCURACY",
      "evidence": [{"source": "ORIGINAL_ANSWER", "quote": "실제 답변의 연속 구간"}],
      "coveredPoints": ["이미 설명한 처리 순서"],
      "improvements": []
    }
  ],
  "uncertainties": [],
  "followUpAxis": "REASONING",
  "followUpQuestion": "남은 근거를 확인하는 질문"
}
```

예시는 축 한 개만 축약했다. 실제 assessments는 TECHNICAL_ACCURACY/REASONING/CLARITY 각각 하나여야 한다.
각 evidence는 1~2개, 인용은 200 코드 포인트 이하. coveredPoints와 improvements는 축마다 각각 0~2개,
각 항목 500 코드 포인트 이하이며 기존 uncertainties 한도(8개/항목500자), 질문500자 등은 유지한다.
source는 ORIGINAL_ANSWER 또는 FOLLOW_UP_ANSWER. 후자는 종합 평가에서만 사용한다.
종합 평가 출력에는 followUpAxis/followUpQuestion 키 자체가 없어야 한다(초기 평가에서만 둘 다 nullable).
이력서 인용과 답변 인용을 혼동하지 않으며, 추가 답변에서 처음 소개한 내용도 근거로 인정한다.

## 서버 처리 규칙
- 닫힌 필드 집합, 세 축 중복/누락, enum·배열·길이·공백을 먼저 전부 검사한다.
- evidence.quote가 지정된 실제 원답/꼬리 답변의 연속 구간인지 검사한다. 잘못된 인용은 502이며 정상 평가로 저장하지 않는다.
- CORRECT/SUFFICIENT/CLEAR인 축의 improvements는 검증 후 빈 배열로 만든다. 다른 축의 부족함 때문에
  긍정 축에 대한 재설명을 강요하지 않는다. 부정 축에서 실제 필요한 오류 교정과 추가 근거는 유지한다.
- 기존 strengths는 coveredPoints, improvements는 허용된 축별 개선점에서 합친다. 동일 문자열은 순서를 유지해 중복 제거한다.
- summary는 기존처럼 판정 세 축으로 서버에서 작성한다. 숫자 점수를 추가하지 않는다.
- 꼬리 질문은 유효한 followUpAxis가 가리키는 부정 축에 남은 개선점이 있을 때만 허용한다.
  긍정 축이나 개선점이 없는 축을 향한 꼬리는 제거한다. 질문/축 null 조합 불일치는 잘못된 응답이다.
- 충분한 답변의 개선점·불확실성·꼬리를 제거하는 기존 전체 긍정 정책은 유지한다.
- 서버 검사는 문장 의미의 정확성이나 경험의 진위를 보증하지 않는다. AI가 잘못된 축으로 분류할 가능성은 남는다.

## 공개 API·저장·화면
- 공개 Evaluation의 기존 8필드는 유지한다. assessments와 followUpAxis를 추가한다.
- 과거 평가 JSON은 새 필드가 없으면 기존 8필드 그대로 역직렬화/조회한다. 새 필드는 null일 때 출력에서 생략한다.
- 신규 평가 버전은 resume-interview-v5. 과거 레코드와 원래 평가는 재작성하지 않는다. DB 테이블 변경은 없다.
- 기존 모델 파일에 중첩 타입을 추가한다. 새로운 서비스/유틸 파일로 잘게 쪼개지 않는다.
- 화면에는 선택적으로 펼치는 항목별 답변 인용 근거를 추가한다. 기존 기록은 현재 화면 그대로 읽을 수 있다.
- 저장/소유권/동시 제출/꼬리 1회/AI 호출 밖 트랜잭션 경계는 바꾸지 않는다.

## 사례와 비교
- JSON fixture 하나에 가상 사례 10개: 부분 설명+근거 부족 2, 현실적 제약으로 타당한 선택,
  익숙함만 말한 부족한 답변, 명백한 기술 오류, 솔직한 정보 부족, 이력서에 없는 새 설명,
  틀렸지만 명확한 답변, 꼬리로 보완된 답변, 꼬리 후에도 부족한 답변.
- 각 사례에 기대 판정/허용 범위, 이미 답한 사실, 필요한 개선점, 다시 요구하면 안 되는 항목을 기록한다.
- 실제 호출 전 fixture와 기준을 고정한다. 결과를 본 뒤 유리하게 기준을 바꾸지 않는다.
- 기존 v4 커밋과 신규 v5 커밋을 격리된 소스/실행으로 비교한다. 제품에 프롬프트 교체 설정을 추가하지 않는다.
- 호출마다 시도 횟수를 먼저 기록한다. 단계별 최대10/승인 총20, 최소65초 간격, 명시 opt-in,
  재시도 금지 및 안전한 오류 기록. .env의 키는 JVM 내부에서만 로드하고 로그/보고서에 넣지 않는다.
- 판정 일치, 이미 답한 내용 재요구, 이력서 밖 내용 부당 감점, 필요한 지적 누락, 불필요한 꼬리를
  같은 기준으로 사람이 검토한다. 오류면 중단하고 재시도하지 않는다.
- 한 번씩의 10쌍은 일반 성능 보증이나 통계적 유의성 검정이 아니다. 실패/악화/미완료도 보고한다.

## 로컬 portfolio.md
문제 → 대안 → 선택 근거 → 구현·검증 → 트레이드오프/잔여 한계 순서로 프로젝트의 주요 의사결정을 정리한다.
현재 코드·검증 결과·Git 기록만 근거로 쓴다. 가상 이력서의 Redis 성능 수치는 프로젝트 실측 성과로 쓰지 않는다.
오늘 비교 결과는 실제 확보한 범위만 추가한다. AI 보조 구현과 사용자의 설계 결정을 개인이 전부 수작업했다는 식으로 꾸미지 않는다.
내용에 키/비밀번호/개인정보를 넣지 않는다. git check-ignore 및 git ls-files로 로컬 전용 상태를 확인한다.

## 설계 검토에서 확정한 사항
- coveredPoints는 단순히 언급한 주제가 아니라 **실제로 충족했다고 인정한 내용/강점**이다. 틀린 주장을
  이 목록에 넣지 않는다. 오류를 뒷받침하는 evidence에는 실제 잘못된 발언을 인용할 수 있지만 그것을 강점으로 합치지 않는다.
- 종합 평가 사례의 원질문·원답·구형 8필드 initialEvaluation·꼬리 질문·꼬리 답변은 양 버전에 동일한
  fixture로 고정한다. 비교 중 별도의 초기 평가를 생성하지 않는다. 따라서 각 사례의 비교는 고정 맥락의
  평가 단발 비교이며, 전체 대화 진행의 종단 간 검증은 기존 HTTP/DB 회귀와 구분한다.
