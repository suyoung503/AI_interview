# v5 근거 기반 평가 검증

## 범위와 결론

축별 인용·충족 사항·개선점과 웹의 **판단 근거 보기**를 구현했다. 인용 출처·길이·원문 포함, 긍정 축 개선점 제거, 부정 축 꼬리 대상, 구형 기록 호환은 서버/회귀 테스트로 검증했다. DB 테이블과 과거 평가 JSON은 변경하지 않는다.

**실제 모델 품질은 부분 개선이며 전체 통과가 아니다.** 이미 설명한 내용을 명시적으로 다시 요구하는 현상은 이번 표본에서 줄었지만, 미측정 답변을 충분하다고 평가해 필요한 지적을 누락한 회귀가 나왔다. 따라서 이 비교만으로 v5의 전반적 정확도 향상이나 배포·main 병합 준비 완료를 주장하지 않는다.

## 실행 조건

- 모델: `openai/gpt-oss-120b`. 사용자 확인 무료 플랜, 유료 전환·다른 모델·자동 재시도 없음.
- before: `7c7ee01`, `resume-interview-v4`; after: `75e5d9c`, `resume-interview-v5`. 각 커밋의 불변 소스 내보내기로 실행했다. 비교 뒤 제품 프롬프트를 바꾸거나 결과가 나쁜 사례를 재호출하지 않았다.
- 고정 입력/기대: `src/test/resources/quality/evaluation-cases.json`, SHA256 `a2d6bafa3f3f02f410a923335899357e1663585e0fdad62299180c739a603dcb`.
- 가상 사례 10개씩 **총 20회 승인·20회 시도·20회 성공, 오류 0**. 첫 오류 시 중단하는 도구를 사용했으며 승인 잔여 호출은 0이다.
- 응답 저장 후 다음 요청까지 상대 시간으로 65초 대기. 단계 간 첫 요청에도 65초 대기. 예약 시각 간 최소 간격은 67,278ms였다. 예약 간격은 네트워크 왕복 지연 측정값이 아니다.
- before 실행 약 10분14초, after 약 11분38초(각 Maven 전체 실행 시간). 성능 벤치마크가 아니다.
- 종합 평가 2개는 두 버전에 동일한 **고정 구형8필드 초기 평가·꼬리 질문**을 제공했다. 실제 전체 면접을 버전별로 새로 생성한 E2E 비교가 아니다.
- 키는 실행 JVM에서만 읽었고 공개 결과는 가상 입력에 대한 평가·안전한 실행 메타데이터뿐이다.

## 사전 기대와의 대조

고정 기대 축과 사람이 의미를 대조했다. 같은 문구나 특정 구현을 모범답안으로 강제하지 않았으며, 별도 AI 심사 호출은 하지 않았다. 필수 피드백은 7개 사례에만 있고 나머지 3개는 충분한 답변이다.

| 관찰 지표 | v4 | v5 |
|---|---:|---:|
| 세 축이 모두 고정 기대와 일치한 사례 | 8/10 | 8/10 |
| 개별 축 기대 일치 | 27/30 | 27/30 |
| 필요한 교정·정보 부족 피드백 유지 | 7/7 | 6/7 |
| 고정 금지 피드백에 해당한 사례 | 1/10 | 0/10 |

금지 피드백 1→0은 **전체 불필요한 피드백이 사라졌다는 뜻이 아니다.** 명시적 재요구 외에 질문 범위를 넘어선 불확실성은 남았고, 필요한 피드백 누락도 따로 집계했다. 전체 항목 수 감소만으로 품질 개선을 판정하지 않았다.

| 고정 사례 | v4 관찰 | v5 관찰 |
|---|---|---|
| cache-order | 흐름·TTL값 인정, 선택 근거 부족 유지 | 동일. “왜 캐시 우선/30초인가”는 원 질문이 요구한 근거이므로 중복으로 세지 않음 |
| retry-order | 횟수/대기 근거 부족 유지. 설정가능성·오류메시지를 추가 요구 | 근거 부족만 개선점으로 유지. 시스템 전반 정책의 불확실성은 범위 확장 여지 |
| bounded-choice | 저량·지연허용·운영제약의 폴링 선택 인정 | 동일, 브로커 강요/꼬리 없음 |
| familiarity | 익숙함만으로 서비스 적합성 설명 부족. 기술 오류 단정 없음 | 동일. 성능·보안 등을 나열한 불확실성은 여전히 넓음 |
| transaction-error | 외부 문자 취소 불가 교정, 기대 3축 일치 | 교정 유지하지만 잘못된 근거를 `INVALID` 대신 `INSUFFICIENT`로 분류. 답변에 명시한 트랜잭션 내 발송도 미확인으로 다루는 부가 문제가 남음 |
| unknown | 미측정 효과의 비교 측정 필요 지적 | **회귀:** 정직한 미측정을 `CORRECT/SUFFICIENT/CLEAR`로 평가, 필요한 측정 피드백·불확실성·꼬리 모두 없음 |
| new-detail | 이력서 밖 고유ID 설명 수용 | 동일, 부당 감점/꼬리 없음 |
| clear-wrong | Base64 교정·명확성 인정. 근거를 `INSUFFICIENT`로 분류 | 교정·`INVALID/CLEAR`로 기대 일치 |
| follow-sufficient | 충분해진 동시 삽입 설명 인정 | 동일. 원답/꼬리 인용 유지, 추가 꼬리 없음 |
| follow-insufficient | 대상 컬럼 재요구. 기술/설명력도 기대 불일치 | 컬럼 인정, 남은 동시 충돌 근거 유지, 기대 3축 일치. 다만 DB·격리 수준·본인 기여 등 질문 밖 불확실성 6개가 남음 |

## 구현 회귀 및 브라우저

- 격리 빌드 `verify`: **178통과 / 21건너뜀 / 실패·오류0**(총199). 기본 실행에서는 실제 키를 읽지 않고 실호출 검증을 건너뛴다.
- Node 웹 테스트 **11/11**, 별도 일회용 MySQL8 **40/40**. MySQL 검증은 가상 구형 스키마→기존 수동 마이그레이션→Hibernate `validate`와 API 검증이다.
- 정확히 서로 다른3축, 인용1~2개/200코드포인트, 지정 원답·꼬리 답변의 연속 인용, 형식 검증 후 정규화, 진짜 부정 축 개선점 유지, 꼬리 null쌍/단계 종료, 기존8필드 JSON 왕복·버전별 히스토리와 신규 저장을 테스트한다.
- 실제 Groq와 분리한 가상 API/전용 MySQL/18080에서 회원가입→이력서→5질문→원답→꼬리→기록 재조회 확인. 원답/꼬리 출처별 근거가 펼쳐지고 `<b>` 문자열은 HTML이 아닌 텍스트로 표시됐다. 구형 기록 호환은 저장/HTTP 테스트로 검증했으며 이번 브라우저에서는 신규 기록만 확인했다.
- 기존8080 v4 서버·실행 JAR·DB는 교체하지 않았다. 이번18080 미리보기와 전용 컨테이너만 종료했다.

## 한계와 다음 검증

정확한 인용은 **그 답변을 평가가 제대로 이해했다는 증명**이 아니다. `unknown`의 인용은 정확했지만 질문 충족 판정은 틀렸다. 긍정 축의 개선점 제거도 모델의 잘못된 긍정 판정을 바로잡지 못한다. 의미가 비슷한 강점의 중복과 과도한 불확실성도 남는다.

사례당 각1회, 작은 가상 표본, 한 모델의 결과이며 통계적 우월성·재현율·다른 사용자 이력서로의 일반화를 입증하지 않는다. 후속 작업은 정직한 정보 부족과 질문 충족을 구별하는 일반 평가 지시, 잘못된 근거와 단순 부족의 구별, 불확실성 범위를 보완하고 **새로 승인된 호출 예산과 별도 검증 표본**으로 확인하는 것이다. 이번 승인20회는 소진되어 추가 호출을 하지 않았다.

원문 평가·축별 근거·사례별 수동 판정은 [가상 비교 증거](resume-interview-v5-comparison.json)에 보존했다. 개인 `portfolio.md`는 이 결과물과 별개인 로컬 전용 파일이며 Git에 포함하지 않는다.
